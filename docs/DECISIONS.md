# Design decisions

Running log of choices made where the brief left room. Newest at the bottom of each section.

## Process
- **D-001 Branching.** Work is on `feature/core-mvp` (from up-to-date `main`), committed per phase, **not pushed** (per brief).
- **D-002 Baseline fixes.** `Milestones.jsx` had a JS syntax error breaking `npm run build`; `backend/package-lock.json` was out of sync with `package.json`. Both fixed before Phase 1.

## Ports / config
- **D-003 Frontend port = 3000.** `.env.example` said 3000, `server.js` and `vite.config.js` said 3001. 3000 chosen (matches the documented example); all three now agree.
- **D-004 `VITE_API_BASE_URL` empty in dev.** The example pointed at :4000 while claiming to use the Vite proxy. It is now empty by default so the proxy is used (no CORS involved); set it only for a separately-hosted production build.

## API conventions
- **D-005 Extra status codes.** The brief lists 200/201/400/401/403/404/409/500. We also use **429** (Ask Autara rate limit) and **503** (AI service down / timed out) because clients and proxies treat them specially. Everything else stays within the list.
- **D-006 Verified is enforced by default.** `requireRole()` rejects unverified therapist/clinician accounts with `403 ACCOUNT_NOT_VERIFIED` on every route; only `/api/auth/me` opts out (`allowUnverified`) so the UI can show the pending page. New routes are safe by default.
- **D-007 Child access errors.** For non-admins every "no access" is the same `404 CHILD_NOT_FOUND` (indistinguishable from a missing child). Admins get `403` because they are never allowed individual child data regardless of existence.
- **D-008 Idempotent child migration.** `GET /api/children` creates the child from the signup profile via an upsert keyed on `{caregiverUid, fromSignupProfile:true}`, only when the caregiver has no Child yet.
- **D-009 AI service health is public.** `GET /health` on FastAPI needs no key (Docker healthcheck, reveals only "ok"); everything else requires `X-Internal-Key` and fails closed if the key isn't configured.
- **D-010 DNS override only for Atlas.** `server.js` forced public DNS resolvers for every URI; that breaks plain `mongodb://` hosts inside Docker. It now applies only to `mongodb+srv://`.

## Testing
- **D-011 Backend test DB.** Tests use `TEST_MONGODB_URI` if set (CI uses a `mongo` service container) and otherwise `mongodb-memory-server`. In the authoring sandbox the MongoDB binary host was blocked by the egress policy, so local runs used FerretDB (Mongo wire-compatible, SQLite). FerretDB lacks `$avg`, date operators and `$facet`, which shaped the aggregation design (D-012).
- **D-012 Aggregations use only `$match/$group/$sum/$sort/$limit`.** Averages are computed from `$sum` ÷ count in JS; hour-of-day / weekday / week-start are stored on each log at write time in the *user's local time* (client sends `tzOffsetMinutes`). This is also more correct than grouping in UTC (a 4pm meltdown must land in the 4pm bar).

## Screening (Phase 2)
- **D-013 ⚠ M-CHAT-R item wording is UNVERIFIED.** The sandbox could not reach any host that publishes the official instrument (mchatscreen.com, university and clinic PDFs were all blocked by the egress policy). The 20 item texts in `ai-service/app/screening/mchatr.py` were entered from memory. They are flagged (`ITEMS_VERIFIED_AGAINST_SOURCE = False`), the API reports `wordingVerified: false`, and the wizard shows a visible "development build" notice until the team compares every item word-for-word with the official PDF and flips the flag. The scoring rules (items 2, 5, 12 reverse-scored; 0–2 / 3–7 / 8–20) come from the brief.
- **D-014 One source of truth for the questionnaire.** Items, domains and copyright live only in the AI service; Node caches `GET /instrument` for 10 min and exposes it as `GET /api/screenings/instrument`. The frontend never duplicates item text.
- **D-015 Child age is computed on the server** from the stored date of birth (never sent by the client), so the 16–30 month check (`AGE_OUT_OF_RANGE`) can't be bypassed.
- **D-016 `INSIGHTS_READY` = "risk score computed".** The brief's lifecycle reuses this name; the LLM insight text is a separate `Insight` document generated on demand by a clinician. A scorer outage never returns an error to the caregiver: the screening is saved as `PROCESSING_FAILED` and `POST /:id/retry` re-runs it.
- **D-017 What each viewer sees.** Caregivers never see the ML `modelProbability` (a bare probability is easy to misread). Clinician override (tier + reason) and reviewed status are shown to the caregiver only once the screening is `REVIEWED`; clinician annotations stay internal.
- **D-018 Domain grouping** (joint attention, social engagement, communication, imitation/play, sensory/motor) is Autara's own, has no clinical validation, and is labelled as such in code, API and UI.
- **D-019 ML model** uses raw yes/no answers as features (logistic regression, class-balanced, 5-fold stratified CV). `train.py` refuses to run without a CSV, detects label leakage (≥98% agreement with a rule threshold) and writes it into the model card. Tests of the pipeline use random noise CSVs in tmp dirs and assert mechanics only.
- **D-020 Frontend tests** use Vitest + Testing Library with the API and auth context mocked (Firebase can't be exercised offline).

## Behaviour tracking (Phase 3)
- **D-021 Local-time facets stored per log** (`local.hour`, `local.weekday` Mon=0, `local.weekStart`), computed from the client-sent `tzOffsetMinutes` (see D-012). Editing a log's time recomputes them.
- **D-022 One `$sum` per `$group`.** Count and intensity-sum are separate small aggregations merged in JS. Real MongoDB handles several accumulators fine; the Mongo-compatible engine used for local tests did not, and separate pipelines are also trivial to read.
- **D-023 Who can write logs:** caregiver, patient, therapist. Verified care-team clinicians can read logs and summaries but not create them (per brief). Edit/delete: author only, both audited.
- **D-024 Charts:** Recharts, lazy-loaded (only chart pages download it). Single series → one brand hue; every chart has loading / error+retry / empty states and a "View as table" switch; the trigger heat table always prints the number in the cell (colour is never the only channel).
- **D-025 Behaviour notes** are free text that may later be sent to the LLM as evidence: the form asks users not to include names and the evidence builder (Phase 5) truncates notes.

## Dashboards (Phase 4)
- **D-026 🔧 Fixed a startup crash on `main`:** `lib/firebaseAdmin.js` used the namespaced API (`admin.apps`, `admin.credential.cert`, `admin.auth()`), which firebase-admin v14 (the version in `package.json`) no longer exports, so the server could not start. Rewritten with the modular API (`firebase-admin/app`, `/auth`), still exposing `auth()`. A test now initialises the real module in a child process (mocks had hidden this).
- **D-027 Clinician actions auto-open the case.** Annotate / override / review on an `INSIGHTS_READY` screening first moves it to `UNDER_CLINICAL_REVIEW`; `POST /:id/open` does the same explicitly and is idempotent (the case page calls it on load). `REVIEWED` is locked (409). Override to the same tier is rejected (`NO_CHANGE`); the original rule tier is always preserved in `originalTier`.
- **D-028 Therapists are read-only on screenings**, can log behaviours and write session notes; session notes are readable only by verified care-team professionals (never caregivers).
- **D-029 Derived notifications.** `GET /api/me/notifications` is computed from real data (recent reviews, failed scorings, queue size, verification queue) — there is no notification store. "Read" state lives in localStorage only.
- **D-030 Reject = `verificationStatus: 'rejected'`.** Added to `User` so rejected sign-ups leave the pending queue and can be re-approved. `PATCH …/verify {verified:false}` both rejects a pending account and revokes an approved one (audit action `USER_VERIFICATION_REVOKED`).
- **D-031 Caregiver dashboard overview endpoint.** `GET /api/children/:id/overview` returns the stat-card numbers, trend, latest domain breakdown and derived "open actions" in one call instead of five.
- **D-032 The mock adapters are deleted** (care team, recent activity, notifications). `AskAutaraCard` and `ReportsSection` are not on the dashboard until their real backends land in Phases 5–6.
- **D-033 `.db-two-col`** was referenced by the original dashboard but never defined in CSS; it is now.

## RAG, insights and Ask Autara (Phase 5)
- **D-034 Model names.** Defaults are `LLM_MODEL=gemini-3.5-flash` and `EMBEDDING_MODEL=gemini-embedding-001` (text-only, stable), both env-configurable. They come from web search results (Google's docs host was blocked from the sandbox), so **confirm them at https://ai.google.dev/gemini-api/docs/models before deploying**. `gemini-embedding-2` (multimodal) exists but is not needed for text. Changing the embedding model requires `python -m app.rag.ingest --reset`.
- **D-035 Provider interface.** `app/llm/base.py` defines two methods (`generate_json`, `embed`); `gemini.py` implements them with the `google-genai` SDK. Adding OpenAI = one more class + a branch in `factory.py`. Tests use a fake provider; there is deliberately **no** fake provider selectable by env (a canned "AI" in a demo would be misleading).
- **D-036 Retrieval stack.** ChromaDB (cosine) persisted to `ai-service/storage/chroma/`; LangChain only for `RecursiveCharacterTextSplitter`; PDFs read with `pypdf` directly (page numbers stay exact). Chunk size uses ≈4 characters per token (600 tokens ≈ 2400 chars, overlap 80 ≈ 320) so no tokenizer download is needed. Chunk ids are SHA-256 of `file|page|index|text`; re-ingest skips unchanged chunks (no re-embedding, no duplicates) and prunes chunks that disappeared from an edited file.
- **D-037 Only approved sources are ingested.** A file must be listed in `knowledge/sources.yaml` (title, publisher, url, version, docType) — unlisted files are reported and skipped; paths escaping the folder are refused. Patient data has no path into the index.
- **D-038 Similarity threshold** default `RAG_MIN_SIMILARITY=0.55` is a starting guess, not a measured value. Tune it with `python -m eval.run` once real documents are ingested.
- **D-039 Validator = the safety core** (`app/insights/validator.py`, `app/safety.py`). Rejects invalid JSON/schema, unknown evidence ids (checked per type), references not matching a retrieved chunk (source + page), empty uncertainty, and banned diagnostic phrases; one retry with the reasons, then `failed`. The banned list is negation-aware only for meta-talk (a sentence that *denies* being a formal diagnosis is fine) — statements that rule a condition *out* stay banned, because excluding a condition is also a diagnosis. False positives cost one retry; false negatives are the risk we design against. The real eval run found one bug in the dosing pattern (it matched the refusal message) — fixed and covered by tests.
- **D-040 Empty corpus.** Retrieval returns `[]` without touching the LLM, insights are still generated from patient evidence (`references: []`, plus an appended uncertainty note added *in code*, not left to the model), and Ask Autara answers "No reference material has been loaded yet" **even without an API key**.
- **D-041 Insights on failure.** A blocked/invalid generation is stored as a `failed` Insight with reason codes only (never the raw LLM text); an unreachable AI service returns 503 and stores nothing. Each generation creates a new Insight (history is kept). Therapists see approved insights only; caregivers see only `caregiverSummary` of an approved insight. There is no clinician editing of AI text — approve or don't.
- **D-042 Evidence minimisation.** Node sends the 20 answers (+ item text), flagged items, domains, a compact behaviour summary, ≤20 recent logs (ids, categories, notes cut to 160 chars) and age in months. The child's name is replaced with `[child]` inside notes; other names a caregiver types cannot be detected, hence the "avoid names" hint in the log form. The AI service rejects unknown fields (`extra="forbid"`).
- **D-043 Ask Autara guardrails run before any retrieval or LLM call** (regex: urgent safety → medication → diagnosis/"level"); answers are validated (citation labels must exist, ≥1 citation when answering, no banned/dosing text). Rate limit is in-memory (20/hour/user, `ASK_RATE_LIMIT_PER_HOUR`); it resets on restart and is per process — use Redis if this ever runs on several instances. Questions are not stored.
- **D-044 Python venv.** `ai-service/.venv` is used locally/CI (system PyYAML in Debian images can't be upgraded by pip).

## Reports and analytics (Phase 6)
- **D-045 Who can export.** Clinicians on the care team can export any scored screening; caregivers/patients only REVIEWED ones of their own child; therapists cannot (read-only role). Two audiences: the clinician copy includes the approved insight in full (with sources) and annotations; the caregiver copy has the plain-language summary and the override reason only.
- **D-046 Reports carry no identifiers:** child *initials* + age in months, dates; the file name uses initials + date. Every PDF page has the disclaimer in its footer (asserted in tests by extracting the text of a multi-page PDF). PDFs are generated on demand (pdfkit, built-in Helvetica — so no arrows/emoji; the render was checked visually), never stored; only a `Report` history row is.
- **D-047 CSV** is one file with a `record_type` column (`note` disclaimer row, 20 `screening_answer` rows, then `behaviour_log` rows) and neutralises spreadsheet formula injection (`=`, `+`, `-`, `@` prefixes).
- **D-048 Analytics privacy (k = 5).** Every count below 5 is returned as `null`. Because a lone hidden bucket can be recovered by subtraction from a published total, **secondary suppression** also hides the smallest visible bucket in that distribution (e.g. tiers `{low:12, medium:6, high:2}` → `{low:12, medium:null, high:null}`). Median hours-to-review needs ≥5 reviewed screenings. The verification-queue size is reported exactly because the admin already sees that queue in full. With small demo data most figures will read "<5" — that is the rule working, not a bug.
- **D-049 Analytics are computed in JS from lightweight `find().select()` queries** (capped at 50k docs) and per-role `countDocuments`; fine for an MVP, revisit with Mongo aggregation if data grows.

## Quality, demo data, docs (Phase 7)
- **D-050 CI** (`.github/workflows/ci.yml`): three jobs (backend with a `mongo:7` service container via `TEST_MONGODB_URI`; ai-service pytest on Python 3.11; frontend Vitest + build). Each was also run from a clean checkout (`npm ci`, fresh venv). **The backend suite has only been run against a Mongo-compatible engine locally (the real MongoDB binary was blocked in the sandbox); the first CI run is its first run on real MongoDB.**
- **D-051 `seed:demo`** computes M-CHAT-R scores locally with the same official rules (offline-safe), tags its rows (`demoTag`) so re-runs replace only demo rows and keep anything users added, and verifies the two professional accounts for demo convenience. All names are fictional and marked "(demo)". A test runs the real script against a throw-away database.
- **D-052 API docs cannot drift:** `tests/apiDocs.test.js` walks the Express router and fails if any route is missing from `docs/API.md`. `tests/contentSafety.test.js` scans UI/backend/docs sources for diagnostic wording.
- **D-053 Docker.** `docker-compose.yml` starts Mongo + backend + AI service (health-checked; the AI port is not published). It was validated with `docker compose config` only — the Docker daemon wasn't available in the sandbox, so `docker compose up` has not been run.
- **D-054 Visual check.** The UI was exercised in headless Chromium at 360px and 1280px using a throw-away harness (Firebase and the API swapped for fixtures, not committed). It found and fixed horizontal overflow on six pages (flex `min-width`, a visually-hidden span inside scrollable tables, the child switcher). No real Firebase login flow was exercised in a browser.
- **D-055 Mobile tab bar** shows the first five nav items; on the caregiver role "Reports" is the sixth, so it is reached from the dashboard's Reports section (or the sidebar on desktop).
